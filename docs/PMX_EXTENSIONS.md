# The extra data an export carries

An exported `.pmx` is a plain MMD file first. On top of that the exporter writes a few things an MMD file has
no field for, all of it as **text in comments** so that a reader which knows nothing about it sees a comment
and a reader that does (the Blender uma addon) can turn it into a shader or a driver. This document defines
that text, so it can be decoded by hand in a year without the exporter, the addon or this repository.

Nothing here is needed to load, pose or render the model.

The **reader side** of this contract - what the Blender uma addon may assume, what it must tolerate, and what
it does with a file whose texture folder did not travel with it - lives in that repository at
`uma_addon/docs/PMX_METADATA_CONTRACT.md`. Keep the two in step: this file defines what is written, that one
defines what may be relied on.

## The metadata format, and how it changes

Every export states the version of this format on its own line of the model comment:

```
metadata format: 2
```

**A missing line means version 1** — whatever the exporter wrote before the line existed. A legacy file is
therefore a supported input rather than a special case, and no reader may require the line.

### What a reader must tolerate

1. **Unknown keys, tokens and lines are ignored, never an error.** That is what makes additions safe.
2. **Absent tokens mean absent features.** No `morph=` means nothing to drive; no `wet=` means no variant
   files. Nothing may fall back to a guess.
3. **Never gate on the application version.** The `Generated by UmaViewer <version>` line above it is for
   humans: it says which build wrote the file, not what the file contains. Two builds of the same metadata
   version can carry completely different morphs.

### What a writer may do without bumping the version

Adding a key, a token, a comment line, or an optional field at the end of an existing token. A version 1
reader still understands the parts it knows and ignores the rest.

### What forces a bump

A change where a reader that understood the previous version would get a *wrong answer* rather than no
answer: renaming a token, removing one, or redefining what a value inside one means. A bump obliges the
writer to keep the old spelling for at least one release (write both), so the version is a warning, not a
cliff.

### What this version does NOT cover

It covers the *format* of the text above. It says nothing about three other contracts, which change under it
without a bump, and which are where users actually get hurt:

| contract | example | how a reader stays compatible |
|---|---|---|
| morph names | `EyeBrow_1_R(WaraiA)[M_Face]` (mode 0) vs `Brow_WaraiA_R` (mode 2) | `Tools/pmx_inspect.py check` accepts all three spellings, and the addon's eye lookup does too. A reader that only knows one spelling is reading a format it was not written for |
| deploy shape-key names | `Manga_*` today, `@_@`/`✦_✦`/`Tear_L` before 2.34 | `MorphDrivers.report_export` reads both, deliberately: those files are still in people's projects |
| material property names | `_CheekRate`, `Tear_Scroll` named by a `morph=` token | a reader should say so when a token names a property the material does not have - Blender creates a custom property instead of failing, so the mistake is silent |

A file-name contract rides with them (`<map>_blush.png` beside the map it was baked from); it is documented
per token below and is not versioned either.

### Changelog
| format | what it added | first written by | readable by |
|---|---|---|---|
| 1 | model `extra morphs:` / `object morphs:`; material `uma1` + shader keys, `morph=`, `blend=multiply`, `scroll=CxR` | ≤ 2.34 | the addon's `MorphDrivers`; the vertex-morph half needs a Blender pass that reads the tokens |
| 2 | model `texture variants:`; material `wet=`, `dirt=` (both additive) | this build (`Config.PmxTextureVariants`, off by default) | a version 1 reader ignores them and loses nothing but the variant wiring |

`uma1` is the per-material marker of the shader-key line. It is written but **read by nothing**, and it is
not a substitute for the line above: one version for the whole format is what a reader can act on.

## Where the text goes
| where | what mmd_tools does with it |
|---|---|
| model comment, `Description` and `DescriptionEn` | `mmd_root.comment_e_text` (a Text datablock) |
| material comment | `material.mmd_material.comment` |

Both are ordinary PMX strings. They are never parsed by MMD itself.

## The model comment

```
<name>
Generated by UmaViewer <version>, Copyright Cygames
Link : https://github.com/katboi01/UmaViewer
metadata format: 2
export settings: morph_names=unified extra_morphs=on texture_variants=off a_pose=on uma_material_fields=on
extra morphs: material comments carry a 'morph=' token (<morph>:<bind type>:<locator part>:<property>) that drives what a pmx cannot hold; see docs/PMX_EXTENSIONS.md
object morphs: Manga_Ctrl:Enable:ScaX:pfb_eff_chr_emo_eye_000>mtl_eff_chr_emo_eye_000,...;Cheek_Ctrl:Enable:PosX:M_Tear_L>mtl_chr1001_00_tear;...
```

The first three lines are the old model info. `metadata format:` and `export settings:` are written on
**every** export (a file without the first is version 1; see
[the metadata format](#the-metadata-format-and-how-it-changes)). `extra morphs:` and `object morphs:` appear
only when `Config.PmxExtraMorphs` is on (it is on by default), and only when the character has such morphs.
`texture variants:` appears only when `Config.PmxTextureVariants` is on (off by default) - see
[the texture variants](#the-texture-variants).

`object morphs:` is a `;`-separated list of `morph:bind type:locator part:objects`:

| field | meaning |
|---|---|
| `morph` | the morph's name, e.g. `Manga_Ctrl`, `StaticTear_Ctrl`, `Tear0_Ctrl` |
| `bind type` | one of `Select`, `EyeSelect`, `Enable`, `TearSide`, `TearWeight`, `TearSelect`, `TearSpeed` |
| `locator part` | which component of the locator transform drives it: `PosX`/`PosY`/`PosZ` or `ScaX`/`ScaY`/`ScaZ` |
| `objects` | the (comma separated) objects the morph shows or hides: the object's name with the runtime's ` (Clone)` stripped, then `>` and the material(s) it is *drawn with*, joined by `+`. Omitted, colon and all, when a bind has no objects (the tears). The material is what a consumer acts on - `pfb_eff_chr_emo_eye_000` is drawn by `mtl_eff_chr_emo_eye_000` here, which looks like a rename and is not one. |

## The material comment

One line, starting with `uma1`, of space separated `key=value` pairs. The shader keys (`toon_step`,
`face_shadow_alpha`, `mask_r1`, `triple`, …) are documented by the addon's Shading operator; every one of them
is a value the game sets on that material and an MMD material has no field for.

When `PmxExtraMorphs` is on, the same line also carries one `morph=` token, holding every extra morph that
binds this material:

```
morph=<morph>:<bind type>:<part>:<property>[,<part>:<property>...][;<morph>:...]
```

| field | meaning |
| `morph` | the morph's name |
| `bind type` | `Texture` (swap a texture and set a float) or `Shader` (set a float) |
| `part` | the axis of the morph's own driver the game reads: `ScaX`, `ScaY`, `ScaZ`, `PosX`, … |
| `property` | the material property the game writes, e.g. `_CheekRate`, `_faceShadowAlpha` |

Only `Texture` and `Shader` binds appear here, because they are the two that end up on a material. Everything
that shows or hides an object is in the model comment instead, since no material comment can hold it.

One more token can appear on a material: `blend=multiply`, on a part the game draws by *multiplying* rather
than by blending. The cheek decal is the one that has it - its texture is white where the face shows through
and only drops the green and blue channels where the blush is, and the game's `MultiplyCheek` shader multiplies
it into the face. An MMD material can only alpha blend, so drawn as it is the decal paints a white shell over
the cheeks.

**The map is exported exactly as the game ships it**, and the token is the whole instruction: a consumer that
can multiply does so, and takes the transparency from the same map. The recipe is not a guess - the addon's
"Fix mini umamusume model" operator already does it for minis, which ship the same defect (a multiply map with
no alpha):

* a Mix node in `MULTIPLY` mode, factor 1, second colour a warm tint (`(1, 0.799, 0.597)`), clamped;
* a colour ramp on the map's own value - white up to 0.85, black at 1.0 - into the shader's alpha, so the
  white "no blush" area becomes transparent and the tinted blush stays opaque;
* the multiply result into the base colour.

The exporter used to bake an alpha-only copy of that map instead (`<map>_blush.png`, `alpha = 1 - min(g, b)`
with a reconstructed colour) and draw the decal with it. That is gone: it was a degraded duplicate of what a
shade pass can compute exactly from the same texels, it doubled the files a cheek costs, and it had to be kept
in step with the shading recipe by hand. Two consequences worth knowing: a model exported **for MMD alone** will
show the white shell if its cheek morph is deployed (MMD cannot multiply - leave that morph alone or use the
addon), and the addon must implement the recipe above for the token to mean anything.

The morph that shows the decal is a vertex morph like the others (see below), so the part needs no addon at
all - only its *shading* does.

Worked example, the head of a normal character:

```
M_Cheek   uma1 ... morph=Cheek_Ctrl:Texture:ScaX:_CheekRate,ScaY:_CheekRate,ScaZ:_CheekRate
M_Face    uma1 ... morph=Shade_Ctrl:Shader:ScaX:_faceShadowAlpha
```

and in the model comment, as a real export of character 1001 writes it:

```
object morphs: Manga_Ctrl:EyeSelect:ScaY:pfb_eff_chr_emo_eye_000,pfb_eff_chr_emo_eye_001,pfb_eff_chr_emo_eye_002,pfb_eff_chr_emo_eye_003;Manga_Ctrl:Enable:ScaX:pfb_eff_chr_emo_eye_000,pfb_eff_chr_emo_eye_001,pfb_eff_chr_emo_eye_002,pfb_eff_chr_emo_eye_003;StaticTear_Ctrl:Enable:PosX:M_Tear_L;StaticTear_Ctrl:Enable:PosY:M_Tear_R;Tear0_Ctrl:TearWeight:ScaX;Tear0_Ctrl:TearSide:PosY;Tear0_Ctrl:TearSelect:ScaY;Tear0_Ctrl:TearSpeed:ScaZ;...
```

and for the animated tears (`Tear{n}_Ctrl`), `TearWeight` on `ScaX`, `TearSide` on `PosY`, `TearSelect` on
`ScaY` and `TearSpeed` on `ScaZ`, with no objects — the game applies those to its own particle system.

## The texture variants

When `Config.PmxTextureVariants` is on (it is **off** by default), the export also writes the game's own
variant sets beside the dry maps and says so in two places. Measured on character 1001 costume 00: **8 of the
34 exported maps** have a wet twin and **2** have a dirt map, about **+2.1 MB** on a 2.7 MB texture set - which
is why the option is off.

**The files.** The game ships these as assets of their own, named after the map they belong to, while the dry
maps live inside the part prefabs. That is why a lookup by name is all they need, and why the export can find
them without a table:

| set | named | what a consumer does with it |
|---|---|---|
| wet | `<dry>_wet` - `tex_bdy1001_00_diff` → `tex_bdy1001_00_diff_wet` | **replaces** the dry map; the game swaps the whole set when a race is rained on |
| dirt | the albedo token changes: `…_diff` → `…_dirt` | an **overlay**, not a replacement: the uma shader draws it from its own `_DirtTex` slot, scaled by `_DirtScale` and `_DirtRate` |

Only albedo maps have a dirt version, so a material can carry a wet twin and no dirt map. Files keep the
game's own names, in the same `Texture2D/` folder as everything else.

**The dirt map is three masks in one file, not a picture.** Measured on `tex_bdy1001_00_dirt` (256x256) and
`tex_chr1001_00_face_dirt` (128x128):

| channel | body | face |
| --- | --- | --- |
| R | mean 0.085, sd 0.152, 3.7% above 0.5 | mean 0.008, sparse marks |
| G | mean 0.079, sd 0.151, 3.7% above 0.5 | mean 0.006, sparse marks |
| B | mean 0.081, sd 0.254, 8.9% above 0.5 | **all zero** |
| A | 1.0 everywhere | 1.0 everywhere |

Pairwise channel correlation is within 0.01 of zero and 26% of the body's pixels differ by more than one standard
deviation between R and G, i.e. these are three *independent* layers, not a colour with a shared shape. Neither
map tiles (the wrap seam stands out at 0.13 against 0.01 between neighbours), so a consumer should not repeat it.
The size is the game's own - 981 dirt maps ship, one per body/attachment part, all of this order - and it is the
one map class where a hand-made replacement would beat the asset.

**Which channel is which layer, and what the shader does with them, is not known.** What the interface says:
`_DirtTex` (unbound on every shipped material), a per-material `_DirtRate` **Vector4** and `_DirtScale` scalar
(1.0 on body and hair, 0.3 on the face), plus the globals `_DirtRate` (three floats, 0..1) and the three tints
`_GlobalDirtColor`, `_GlobalDirtToonColor`, `_GlobalDirtRimSpecularColor`. `Gallop.CharaShaderEffectData`
declares an effect index `DATA_SET_DIRT`, and its application is not in the decompile, so there is no reference
maths to copy - a consumer that wants the look defines it. The add-on's version mixes toward one colour by
`max(r, g, b)` times its own `Dirt` property, which is a choice, not a reconstruction.

**The model comment** gains one line, so a reader can tell three states apart without scanning every material:

```
texture variants: wet 8, dirt 2 - the game's own variant maps, written into Texture2D/ under the game's names (<texture>_wet.png, <texture>_dirt.png). A pmx material has one texture slot, so each material names its own with a 'wet=' / 'dirt=' comment token; see docs/PMX_EXTENSIONS.md
```

| what it says | means |
|---|---|
| no `texture variants:` line at all | the export did not ask for them (`PmxTextureVariants` off), or predates the option: there are no variant files beside it |
| `texture variants: none (requested, but …)` | they were asked for, and this character or prop ships none |
| `texture variants: wet N, dirt M` | they were asked for, and these are the family sizes |

**The material comment** gains `wet=` and `dirt=`, each a comma separated list of file names (no folder, no
extension):

```
uma1 ... wet=tex_bdy1001_00_base_wet,tex_bdy1001_00_ctrl_wet,tex_bdy1001_00_diff_wet,tex_bdy1001_00_shad_c_wet dirt=tex_bdy1001_00_dirt
```

A pmx material has exactly **one** texture, so a second map cannot be a material texture: the token is the
only place it can be named, for the same reason `morph=` and `blend=` exist. `wet=` lists files that replace
their dry counterpart — the dry map is the token's name minus `_wet` — and `dirt=` lists the dirt overlays.

**What reads them.** Nothing in MMD. They are for a shader that knows what the maps are: the uma addon binds
them to its own wet and dirt inputs and lets the user drive them. An export with the option off is byte for
byte what it was before the option existed: no files, no tokens, no model line.

## The export settings line

Written on every export, because two exports of the same character can differ completely and the alternative
to saying so is a reader inferring it from the contents:

```
export settings: morph_names=unified extra_morphs=on texture_variants=off a_pose=on uma_material_fields=on
```

| key | values | what it decides |
|---|---|---|
| `morph_names` | `blender_compatible`, `short_english`, `unified` | **renames every morph**, so it decides whether a name a reader looks for exists at all |
| `extra_morphs` | `on`/`off` | the `morph=`/`blend=`/`scroll=` tokens and the deploy vertex morphs |
| `texture_variants` | `on`/`off` | whether `texture variants:` and the `wet=`/`dirt=` files were asked for |
| `a_pose` | `on`/`off` | the rest pose the model stands in (arms 38.5° into the A-pose, or a plain T) |
| `uma_material_fields` | `on`/`off` | whether the material comments carry the uma shader values at all |

Values are **words, not numbers**. The enum's numbering is implementation detail and has already moved once
(`Both` retired, `Unified` 3 → 2), so a reader keying on `2` would silently have read the wrong mode. This
line is also how a *content* change shows itself without a metadata bump: names cannot say which mode wrote
them, but this can.

An absent key means the export predates the key; treat it as the default that was in force then (`unified`,
`extra_morphs=on`, `texture_variants=off`, `a_pose=on`, `uma_material_fields=on`).

## Where the textures live, and what happens when they are not there

A `.pmx` does **not** embed textures. It names them as relative paths (`Texture2D/<name>.png`) and the files
sit in that folder beside it. The FBX path can embed them (`Config.FbxEmbedTextures`); a pmx cannot. So the
folder and the model are one artifact, and they get separated:

* **A missing texture table entry** makes the model render untextured in MMD and Blender. Standard MMD
  behaviour, and nothing here can prevent it.
* **The variant maps are the fragile ones.** `wet=`/`dirt=` files are named by a *comment token* and are not
  in the pmx's texture table, so a cleanup that deletes "files nothing references", or a user who copies only
  the `.pmx`, takes them. That is why `Tools/probe_texture_usage.py` treats tokens as references: without
  that it reports every variant file as a leftover - measured, it called all 13 of a character's variants
  garbage.
* **A model can therefore claim `texture variants: wet 11, dirt 2` and have none of them beside it.** The
  tokens are intent; the folder is reality.

What a reader must do: check that each file it is about to use exists next to the pmx, name each missing one,
and **degrade** - drop that feature and keep the rest working. Never fail an import over a missing variant
map. The reasoning is the same as for `FbxEmbedTextures`: this data is optional by nature, so its absence is a
reporting problem, not an error.

## The deploy morphs

Five of these morphs are *not* just described, they are MMD morphs: they show and hide a decal part, which is
exactly what a vertex morph can do.

| morph | part it deploys | vertices |
|---|---|---|
| `Cheek_Blush` | the cheek blush decal (`mtl_chr1001_00_cheek`) | 54 |
| `Manga_Spin_L/R`, `Manga_Star_L/R`, `Manga_Shut_L/R`, `Manga_Wide_L/R` | the four eye manga (`mtl_eff_chr_emo_eye_000` … `_003`), one morph per eye and expression | 4 each |
| `Tear_Static_L/R` | the static tears (`mtl_chr1001_00_tear`) | 15 each |
| `Tear_Pool_L/R` | the wide animated tear card (`tear001`), deduplicated to one morph per distinct card | 36 |

These are the *only* morphs the exporter adds, and every one of them is a **vertex** morph. The tall rolling tear
card (`tear000`) is deliberately not among them: a tear that cannot move reads as a mistake, so it stays collapsed and
is simply not in the model. Older exports carried
two more stacks - `Manga_Spin_*_Turn1..7` rotations and `<card>_Sheet1..7` sprite-sheet steps - which were removed:
nothing in the pipeline can use them (Blender cannot animate a uv layer, so the add-on drives the same two effects
from the material with the `scroll=`/`Spin_*` route), and they were 42 of a character's 249 morphs. The reasoning and
what it costs are in `EXTRA_MORPHS.md` under "Why the export carries no UV morphs".

A pmx is read with every morph at 0, so the state the model must *rest* in is the collapsed one: every vertex
of a decal part is written on a single point inside the head, which makes it a handful of zero-area triangles -
invisible, and drawn nowhere - wherever that point is. Each deploy morph carries the offsets that put its part
back. At weight 1 the part is the decal the game shows, moved a hair off the surface it is painted on; at 0 it is
gone.

That hair matters: at the game's own position a deployed decal is exactly coplanar with the face, and a renderer
answers with z-fighting (the blush) or by hiding the decal behind the eye (the manga, as soon as an eye-hide morph
moves it). So the deploy target is offset along the decal's own normal by a fixed fraction of the part's distance
from the head bone - a fraction, not a length, because the file has no physical unit - which measures out at
`0.061 … 0.071` in the file's own units across every decal on 1001.

This is the idiom MMD models use for a hidden accessory: the reference model `Appearance Miku_BDEF_mod-v03`
hides two eye highlights with `HL消1` and `HL消2`, which move 58 and 116 vertices onto a single point each.
It needs nothing but MMD itself - no addon, no drivers, no bones.

The parts stay drawn by their own materials (alpha 1, no outline, no self shadow, no ground shadow), so what hides
them at rest is the geometry, not the material. They are double sided, which is now a belt rather than the
braces: the exporter reverses the winding of a decal part whose polygons face into the head (the mirrored
right-hand instances used to arrive that way - see `HANDOFF_OPTIONS_AND_RELEASE.md`, "The decal winding defect"),
so both eyes face out of the file, but a consumer that culls is still better off not culling a decal.

## How a consumer drives them

Two paths, both from the same tokens:

* **MMD itself** - the deploy morphs above are ordinary vertex morphs, so the five decals can be shown and
  hidden with nothing but MMD's morph panel.
* **the uma addon** - reads `object morphs:` and the material `morph=` tokens and wires them to custom
  properties on the model (the cheek texture pair and `_CheekRate`, the face shadow alpha) for the parts a
  morph cannot hold. The token names the morph, which is the name of the custom property the addon makes.

## The flags

| flag | default | what it does |
|---|---|---|
| `PmxUmaMaterialFields` | `true` | writes the uma shader keys into the material comments, and the specular/outline values an MMD material can hold. `false` gives plain MMD materials. |
| `PmxExtraMorphs` | `true` | carries the morph parts in the mesh, writes the deploy morphs, and writes the `morph=` and `object morphs:` descriptions above. `false` leaves the parts out; the decals then stay wherever the game draws them (visible). |

Both are printed as tooltips in the viewer's settings. With both off the export is an ordinary PMX: the plain
MMD material values, vertex morphs, bones and textures.

## What a user without the addon sees

* The model loads, poses and renders normally.
* Every vertex morph the PMX can hold is there - eyes, brows, mouth, ears - and the fifteen deploy morphs as
well: `Cheek_Blush`, the eight eye manga (`Manga_Star_L` … `Manga_Wide_R`), `Tear_Static_L/R` and the wide
animated card `Tear_Pool_L/R` - 205 morphs on character 1001, and no uv morphs at all.
* The `@_@` turn and the tear sheet scroll are **not animated** without the add-on: their uv-morph stacks were
  removed on purpose (see "Why the export carries no UV morphs" in `EXTRA_MORPHS.md`), so the two decals sit still
  in plain MMD. Everything else described here is unaffected.
* The cheek blush is a pale wash rather than the game's multiply (see `blend=multiply` above), which is the
  one part plain MMD cannot draw as the game does.
* The comments above are visible in the material panel and the model properties, which is the point of them.

## Status

The export side is done and verified on a real export: the parts are in the mesh, the deploy morphs move
exactly their own vertices, and at rest the decal polygon area is 0.000000. The addon side is the material
half - the cheek texture pair and `_CheekRate`, the face shadow alpha - which a vertex morph cannot hold.
